## 1. Executive Summary & Existing Architecture Mapping

File To Link V2 is an asynchronous Telegram-to-Web streaming and file-delivery gateway. The system ingests files from Telegram bot channels, proxies byte-ranges, generates adaptive HLS streams on demand, generates preview scrub storyboards, and serves a browser-based watch and download interface.

### Existing Architecture Flow:
```
Telegram Servers / FLOG Channel
       │ (MTProto / Pyrogram ByteStreamer)
       ▼
FileStream Backend (aiohttp Web Server)
       │
       ├─► Database (MongoDB): Metadata, Files, PublicLinks, Folders, Jobs
       ├─► TokenService: HMAC / cryptographically secure scoped access tokens
       ├─► StorageService: Multi-worker background storage & FLOG replication
       ├─► MP4MetadataManager: Fast-scrub moov-atom relocation & patching
       ├─► HLSService: Dynamic FFmpeg transcoding ladder (1080p, 720p, 480p)
       └─► ThumbnailService: WebP sprite sheets & WebVTT storyboard previews
       │
       ▼
HTTP Streaming Endpoints (`FileStream/server/stream_routes.py`)
       ├─► GET /gen/{public_id}               (Web Landing / Player Page HTML)
       ├─► GET /get-stream-token/{public_id}  (Token Generation & Source Resolution JSON)
       ├─► GET /stream/{token}                (Direct ByteStreamer with 206 Partial Content)
       ├─► GET /hls/{token}/master.m3u8       (HLS Adaptive Bitrate Master Playlist)
       ├─► GET /hls/{token}/{quality}/...     (HLS Media Playlists & On-Demand .ts segments)
       ├─► GET /thumbnails/{token}/...        (WebVTT & WebP scrub sprites)
       └─► GET /thumb/{public_id}             (Cached Video Poster / Telegram Thumbnail)
       │
       ▼
Browser Web Application (`play.html` + `player.js` + `player.css`)
       │
       ▼
Vidstack Media Player (Web Components: <media-player>, <media-provider>, <media-video-layout>)
```

## 2. Deep Audit of Current Streaming & Player Failures

Our thorough inspection of `play.html`, `app.js`, `stream_routes.py`, `hls_service.py`, and test suites identified several specific failure mechanisms causing the reported problems:

### Failure 1: The Indefinite "Connecting Secure Edge Stream..." Lock
* **Mechanism:** In `play.html`, the overlay (`#playerOverlay`) with text `"Connecting Secure Edge Stream…"` and `#playerOverlaySpinner` is turned on synchronously inside `startStreaming()`. The overlay is positioned with `absolute inset-0 bg-black/85 backdrop-blur-sm z-20`, which completely covers the player and video.
* **Root Cause:**
  1. Hiding the overlay is bound solely to `can-play`, `playing`, and `loaded-metadata` events on the `<media-player>` element.
  2. If the stream encounters a delay (such as FFmpeg generating the first segment for an MKV/HEVC transcode in `ensure_segment`), or if the browser blocks autoplay due to mobile media policies without audio mute, or if an HLS playlist retry occurs, none of these three events fire immediately.
  3. There is **no timeout guard**, no progress indicator, and no status transition (e.g. from "Preparing stream..." to "Transcoding initial segment..." to "Ready").
  4. The user is trapped staring at `"Connecting Secure Edge Stream…"` indefinitely, unable even to click player controls because the overlay intercepts all pointer events.

### Failure 2: Black Screen Before Playback
* **Mechanism:** When transitioning from the file information card (`#managerView`) to the player card (`#playerView`), the video area defaults to a blank black rectangle.
* **Root Cause:**
  1. `<media-poster>` points directly to `/thumb/{public_id}`. If the video thumbnail is still being generated by the worker, or if Telegram FLOG channel extraction fails, the image request 404s.
  2. While the media element waits for decoded video frames, no fallback poster or skeleton frame is rendered, resulting in a black void.
  3. When an unsupported video codec (e.g. HEVC 10-bit in an MKV container) is sent to a browser that cannot natively decode HEVC, the browser video decoder emits a decode error or hangs silently, remaining completely black.

### Failure 3: Mixed and Obsolete Player Framework Residue
* **Mechanism:** The repository historically contained Plyr.js (`plyr.js`, `plyr.css`) and standalone HLS.js (`hls.min.js`), along with partially refactored Vidstack custom elements and bespoke inline DOM handlers.
* **Root Cause:**
  1. `play.html` contained over 380 lines of unstructured, monolithic inline JavaScript containing card spotlight listeners, duration formatting, image loading, download handlers, token fetchers, custom element racing, and Vidstack event listeners.
  2. Player state was spread across loose global variables (`hasResumed`, `isFetchingStreamToken`, `cachedStreamData`, `streamTokenFetchTime`, `streamAbortController`).
  3. No finite state machine (FSM) existed to coordinate state transitions (`IDLE`, `LOADING`, `READY`, `PLAYING`, `PAUSED`, `BUFFERING`, `STALLED`, `RECONNECTING`, `ERROR`, `ENDED`).

### Failure 4: Codec & Container Incompatibility (MKV / HEVC vs Direct Stream)
* **Mechanism:** The sample file `The.Last.Ship.S03E06.Dog.Day.720p.WEB-DL.2CH.x265.HEVC-PSA.mkv` is Matroska with H.265/HEVC.
* **Root Cause:**
  1. Browsers (specifically Chrome on Windows/Linux and non-Safari desktop browsers) do not natively support Matroska container playback via `<video src="...">`, and many do not have hardware HEVC decoders.
  2. Vidstack is a UI framework and does not remux or decode codecs that the browser cannot decode.
  3. The backend does possess an on-demand HLS transcoding pipeline (`HLSService`) that can transcode MKV/HEVC to H.264/AAC TS segments via FFmpeg. However, the frontend source resolution was crude: it simply checked `data.is_native_playable` vs `data.hls_url`, without testing actual browser codec support (`MediaSource.isTypeSupported` / `canPlayType`), without communicating transcode progress to the user, and without offering an honest fallback (direct download / external player).

### Failure 5: Mobile UX & Fullscreen Inconsistencies
* **Mechanism:** On iOS Safari and Android Chrome:
  1. Viewport scaling constraints (`user-scalable=no, maximum-scale=1.0`) combined with inline element padding caused controls to clip.
  2. Native fullscreen on iOS (`webkitEnterFullscreen`) operates on HTMLVideoElement directly rather than custom elements, causing Vidstack custom layout controls to detach or disappear unless properly delegated.
  3. Small touch targets in menu overlays violated accessibility standards.

## 4. Source Type Strategy

The source resolution layer maps media metadata to browser playback capabilities:

| Container / Codecs | Browser Capabilities | Resolved Player Source | Fallback / UI Behavior |
| :--- | :--- | :--- | :--- |
| **MP4 (H.264 / AAC)** | Universal native playback | Direct progressive stream (`/stream/{token}`) | Instant start, hardware acceleration, full Range seeking |
| **WebM (VP8/VP9 / Opus)** | Universal (Chrome/Firefox/Edge) | Direct progressive stream (`/stream/{token}`) | Instant start, byte-range scrubbing |
| **MKV / HEVC (x265)** | HLS supported (`application/x-mpegurl`) | Adaptive HLS stream (`/hls/{token}/master.m3u8`) | Informative "Transcoding stream..." badge; if transcode times out, suggest Direct Download / VLC |
| **Audio (MP3, M4A, FLAC)** | Universal native audio | Direct stream with `<media-audio-layout>` | Audio waveform / metadata layout |
| **Unsupported Container** | Neither native nor HLS decode possible | Notifies user with actionable guidance | Clean modal offering Direct Download button and VLC/Infuse instructions |

## 5. Architectural Invariants Preserved
1. **Zero Memory Buffering:** Large 200MB–2GB files stream strictly through chunked async generators (`ByteStreamer.yield_file`), never loading full files into server RAM.
2. **Session & Token Scoping:** Stream tokens remain locked to `fs_page_session` cookies and path-scoped HMAC tokens; no direct database IDs or storage URLs are leaked.
3. **Backward Compatibility:** All existing endpoints (`/dl/`, `/stream/`, `/file/`, `/hls/`, `/thumb/`, `/get-stream-token/`) preserve exact HTTP semantics, status codes, and header structures.
4. **Test Suite Integrity:** The existing 506 unit and integration tests across the system must continue to pass 100%.
