1.2 Architectural Roles & Boundary Definitions
--------------------------------------------------------------------------------
The system divides responsibilities across specialized software layers:

  1. Telegram MTProto Interface:
     Managed via Pyrogram / Pyrofork MTProto client libraries. Handles raw Telegram
     DC connections, encryption keys, authorization sessions, and update loops.

  2. Primary Dispatcher (Client 0):
     The public Telegram bot account defined by `Telegram.BOT_TOKEN`. Client 0 is
     the user-facing interface for incoming files, `/start` deep links, inline
     buttons, user settings, and administrative operations.

  3. Secondary Storage Worker Mesh (`multi_clients`):
     Headless MTProto clients instantiated from environment variables
     `MULTI_TOKEN1`, `MULTI_TOKEN2`, etc. These workers execute background file
     archiving without handling interactive updates.

  4. Durable State & Storage Tier (MongoDB):
     The single source of truth for the system. Manages metadata documents,
     folder hierarchies, public link tokens, user permissions, and persistent
     storage jobs.

  5. Streaming & Media Delivery Engine (`aiohttp.web`):
     High-throughput asynchronous web application handling public file resolution,
     browser playback pages (Plyr.js), byte-range streaming, direct downloads, and
     promotional URL shorteners.

1.3 Multi-Bot Client Pooling & Worker Mesh (clients.py)
--------------------------------------------------------------------------------
The multi-bot architecture overcomes single-account Telegram MTProto throughput
bottlenecks (such as 420 FloodWait limits and concurrent connection constraints).

  - Client Initialization Lifecycle (`FileStream/bot/clients.py:initialize_clients`):
    1. Scans environment variables using regex `^MULTI_TOKEN(\d+)$`.
    2. Identifies all configured worker tokens and sorts them numerically by index.
    3. Retains Client 0 (`FileStream`) as the primary command controller.
    4. For each secondary index `i`, initializes an independent Pyrogram `Client`
       configured with `in_memory=True`, `sleep_threshold=0`, and `no_updates=False`.
    5. Starts each secondary client asynchronously using `asyncio.gather()`.
    6. Attaches secondary worker identity attributes:
       `client.client_index = i`, `client.id = me.id`, `client.username = me.username`.
    7. Registers dedicated secondary handlers via `setup_secondary_worker_handlers()`.
    8. Registers the client into `StorageService._clients_dict`.
    9. Sets initial workload counter `work_loads[i] = 0` and initializes stats
       via `ensure_client_stat(i)`.

  - Secondary Worker Isolation Pattern:
    To prevent secondary workers from processing user commands or creating duplicate
    database documents, `is_secondary_worker(client)` checks:
    ```python
    def is_secondary_worker(client) -> bool:
        idx = getattr(client, "client_index", 0)
        return int(idx) > 0
    ```
    All interactive plugins in `FileStream/bot/plugins/` (e.g. `stream.py`, `start.py`,
    `admin.py`) immediately return if `is_secondary_worker(bot)` evaluates to True.

1.4 Dynamic Load Balancing & EWMA Scheduling (client_balance.py)
--------------------------------------------------------------------------------
Streaming workload distribution among active MTProto clients is managed by
`FileStream/utils/client_balance.py`:

  - Client Selection Algorithm (`choose_best_client`):
    Given a pool of available client indices, the selector:
      1. Inspects client cooldown timers (`cooldown_until`). Any client in active
         cooldown (e.g., following a FloodWait) is filtered out.
      2. If all clients are cooling down, raises `RuntimeError` reporting the earliest
         availability timestamp.
      3. Calculates a lexicographical sorting tuple for each healthy client:
         `score = (work_load, consecutive_failures, floodwait_count, avg_first_byte_ms, -avg_throughput_bps, index)`
      4. Selects the client with the minimum score (lowest active connections,
         lowest errors, and fastest historical first-byte response).

  - Exponentially Weighted Moving Average (EWMA):
    Updates running latency and throughput metrics using `EWMA_ALPHA = 0.35`:
    ```python
    avg = (current * (1.0 - alpha)) + (new_sample * alpha)
    ```
    This smooths transient spikes while adapting to persistent network changes.

1.5 Bot Client Identity & Deeplink Resolution (client_identity.py)
--------------------------------------------------------------------------------
`FileStream/utils/client_identity.py` provides resilient identity discovery
without making blocking MTProto API calls:
  - `get_bot_username(bot)`: Inspects `bot.me.username` -> `bot.username` ->
    `FileStream.me.username` -> `FileStream.username`.
  - `build_start_link(payload, bot)`: Formats standard Telegram deep-links:
    `https://t.me/{username}?start={payload}`.
  - `build_add_to_group_link(bot)`: Formats group authorization links:
    `https://t.me/{username}?startgroup=true`.

2.1 Lifecycle A: Single File Upload to Multi-Link Streaming Delivery
--------------------------------------------------------------------------------
The single-file upload lifecycle transforms any Telegram media item into public
streaming and download URLs:

```
User Message ────────► private_receive_handler() (stream.py:63)
                                │
                                ├─► verify_user() [Ban check, Whitelist]
                                ├─► Check Active Folder Session (False)
                                ├─► Send ChatAction (UPLOAD_VIDEO / DOCUMENT)
                                ├─► Send Status Message ("⚡ Processing File...")
                                │
                                ▼
                   file_service.process_new_file() (file_service.py:126)
                                │
                                ├─► get_file_info(message) [Extract media meta]
                                ├─► db.normalize_file_doc() [MIME, category]
                                ├─► db.file.insert_one() [Status: PENDING]
                                │
                                ▼
               storage_service.enqueue_storage() (storage_service.py:537)
                                │
                                ├─► db.create_storage_job() [Durable Mongo Job]
                                └─► asyncio.Queue.put_nowait() [Execution buffer]
                                │
                                ▼
                   Worker Task: _worker_loop() (storage_service.py:768)
                                │
                                ├─► db.claim_next_storage_job() [Atomic lock]
                                ├─► Select Client & Target FLOG Channel
                                ├─► client.send_cached_media() / copy_message()
                                ├─► db.mark_job_stored(flog_msg_id, channel_id)
                                ├─► db.file.update_one(storage_status="STORED")
                                └─► audit_manager.enqueue() [Post info card]
                                │
                                ▼
                      gen_link() (bot_utils.py:164)
                                │
                                ├─► db.ensure_public_link_for_file()
                                ├─► Build Stream URL: /watch/{public_id}
                                ├─► Build Download URL: /dl/{public_id}
                                └─► Edit Status Message to Final Ready Card
```

Step-by-Step Execution Trace:
  1. Ingestion:
     User sends media (Video, Document, Audio, Animation, Photo) to the bot.
     `private_receive_handler` intercepts the message (group=4).
  2. Verification:
     `verify_user` checks whether the user is banned (`users.banned == True`).
     If `Telegram.AUTH_USERS` is configured, confirms authorization.
  3. Routing Inspection:
     Checks `folder_service.get_active_session_for_user(user_id)`. If an active
     session exists, redirects to `handle_folder_file`. Otherwise, continues.
  4. Database Persistence:
     `file_service.process_new_file` creates a document in `file` collection:
     ```json
     {
       "_id": ObjectId("..."),
       "file_id": "BAACAgIAAxkBAAI...",
       "file_unique_id": "AQAD...",
       "file_name": "example_video.mp4",
       "file_size": 104857600,
       "mime_type": "video/mp4",
       "user_id": 123456789,
       "time": 1727188800.0,
       "storage_status": "PENDING",
       "is_folder_file": false
     }
     ```
  5. Asynchronous Storage Queue:
     Enqueues a durable storage job in `storage_jobs` collection with
     `job_id = "{db_id}:STORE_TO_FLOG"`. Pushes job reference to `storage_service._queue`.
  6. Worker Execution:
     A background worker claims the job atomically via `find_one_and_update`,
     setting `status = "CLAIMED"` and `lease_until = now + 300s`.
     The worker selects an active storage client and copies/forwards the media
     to the resolved FLOG storage channel (`FLOG_CHANNEL` or `ADMIN_FLOG_CHANNEL`).
  7. Finalization:
     On successful FLOG delivery, updates file document with `flog_msg_id` and
     `storage_status = "STORED"`. Marks job as `STORED`.
  8. User Notification:
     `gen_link` creates a public link mapping in `public_links` and edits the
     processing message with the link card and buttons.

2.2 Lifecycle B: Batch & Folder Processing, Ingestion & Pagination
--------------------------------------------------------------------------------
Batch and folder operations allow grouping up to 1,000 files into a single
shareable folder:

  1. Session Initialization:
     User sends `/folder` or clicks "📁 Start Folder". `start_folder_cmd` invokes
     `folder_service.start_session(user_id)`, inserting a session document into
     `folder_sessions` with `state = "ACTIVE"`.
  2. Multi-File Ingestion:
     As user sends files, `private_receive_handler` identifies `folder_active == True`
     and delegates execution to `handle_folder_file()` in `batch.py`:
       * Verifies file count is within `MAX_FOLDERM_ITEMS` (1,000).
       * Creates file document in `file` collection with `is_folder_file = True`
         and `folder_session_id = session_id`.
       * Enqueues durable storage job with `is_folder_file = True`.
       * Appends `file_id` to session document's `files` array.
       * Updates the interactive folder management panel with throttled UI refreshes.
  3. Interactive Session Inspection:
     Clicking `[📋 View Files]` displays paginated folder contents (5 items per page).
     `_enrich_page_files()` queries MongoDB exclusively for the 5 files in view,
     preventing memory bloat when inspecting 1,000-file folders.
  4. Finalization (`[✅ Done]`):
     Invokes `folder_service.finalize_folder(session_id)`:
       * Transitions session state to `COMPLETING`.
       * Generates a 16-character base62 `public_token`.
       * Creates folder document in `folders` collection:
         ```json
         {
           "_id": ObjectId("..."),
           "user_id": 123456789,
           "title": "Folder 24-Sep-2026",
           "files": ["66f2d...", "66f2e..."],
           "file_count": 25,
           "total_size": 2621440000,
           "public_token": "aB3dE5gH7kLm9PqR",
           "created_at": 1727188800.0
         }
         ```
       * Deletes temporary session from `folder_sessions`.
       * Delivers final folder card with web link `/gfolder/{public_token}`.
  5. Fast Cancellation (`[❌ Cancel]`):
     `folder_service.cancel_session(session_id)` immediately cancels all pending
     storage jobs in MongoDB and enqueues background deletion of all uploaded FLOG
     messages and file documents.

2.3 Lifecycle C: Client Web Range Request to MTProto Chunk Streaming
--------------------------------------------------------------------------------
This lifecycle governs the high-performance delivery of media bytes from Telegram
DCs directly to web browsers without holding full files in memory or local disk:

```
Browser Request ──────► GET /stream/{token} (stream_routes.py:409)
(Range: bytes=0-1048575)        │
                                ├─► validate_access_token(token, kind="stream")
                                ├─► Match Session Cookie (fs_page_session)
                                │
                                ▼
                   media_streamer() (stream_routes.py:480)
                                │
                                ├─► db.resolve_file_reference(db_id)
                                ├─► ensure_flog_media_exists() [Verify Telegram msg]
                                ├─► choose_best_client() [EWMA Load Balancer]
                                ├─► Parse HTTP Range Header -> from_bytes, until_bytes
                                ├─► Calculate Chunk Bounds & Part Count
                                │
                                ▼
                   ByteStreamer.yield_file() (custom_dl.py:176)
                                │
                                ├─► generate_media_session() [Connect to Media DC]
                                ├─► Prefetch Pipeline (STREAM_PREFETCH_CHUNKS)
                                │   │
                                │   ├─► Check Local Disk Cache (stream_cache)
                                │   │   └─► Cache Hit: Read chunk from disk
                                │   │
                                │   └─► Cache Miss: Raw MTProto upload.GetFile()
                                │       └─► Write to Local Disk Cache
                                │
                                ▼
                 aiohttp.web.Response(status=206, body=generator)
                                │
                                └─► Pipe 1MB chunks to client HTTP socket
```

Step-by-Step Streaming Pipeline:
  1. Token & Session Validation:
     Browser requests `/stream/{token}`. The server validates the token in
     `TokenService` and confirms that `token.metadata.session_id` matches the
     `fs_page_session` HTTP cookie.
  2. Range Negotiation:
     `_parse_range(range_header, file_size)` parses the HTTP `Range` header:
       * Single range: `bytes=1048576-2097151` -> `from_bytes=1048576`, `until_bytes=2097151`.
       * Suffix range: `bytes=-1048576` -> `from_bytes=file_size-1048576`, `until_bytes=file_size-1`.
       * Full request: `from_bytes=0`, `until_bytes=file_size-1`.
     Invalid ranges return HTTP 416 Range Not Satisfiable.
  3. Client Selection & ByteStreamer Initialization:
     `choose_best_client` selects the optimal Telegram MTProto client. The server
     retrieves or instantiates a `ByteStreamer(client)` cached in `class_cache`.
  4. DC Media Session Authorization:
     `generate_media_session(client, file_id)` identifies the target Telegram DC
     (`file_id.dc_id`). If the client is not authenticated with that DC, invokes
     `raw.functions.auth.ExportAuthorization` on the main DC and `ImportAuthorization`
     on the media DC.
  5. Chunk Streaming & Prefetching:
     `yield_file` calculates required parts based on `chunk_size` (clamped to 1MB
     due to Telegram's `upload.GetFile` limit). It launches background prefetch
     tasks up to `Server.STREAM_PREFETCH_CHUNKS`.
  6. Hybrid Disk Cache Lookup:
     `LocalStreamCache.get_or_fetch_chunk()` checks for the chunk on disk
     (`{offset:020d}.chunk`). If present, serves from disk. Otherwise, fetches
     via `media_session.invoke(raw.functions.upload.GetFile(...))` and caches to disk.
  7. Client Delivery:
     Yields data chunks into the aiohttp response stream, serving HTTP 206 Partial
     Content with accurate `Content-Range: bytes {start}-{end}/{total}` headers.

2.4 Lifecycle D: Public Links, Shorteners & Ephemeral Token Gating
--------------------------------------------------------------------------------
Protects media origins and integrates monetized link shorteners:
  - Public Decoupling:
    Public URLs format: `/watch/{public_id}` and `/dl/{public_id}`.
    Internal MongoDB ObjectIds, Telegram message IDs, and channel IDs are never
    exposed to public web clients.
  - Ephemeral Token Gating (`TokenService`):
    Visiting `/watch/{public_id}` sets an HTTP-only browser cookie (`fs_page_session`)
    and issues an ephemeral token for the player:
    `token_service.create_access_token(path, kind="stream", expires_in_seconds=300)`.
    Direct requests to `/stream/{token}` fail with HTTP 403 unless accompanied
    by the matching cookie.
  - URL Shortener Integration (`ShortenerService`):
    If URL shorteners are enabled (`db.get_urlshortener_status() == True`),
    link generation routes public links through the configured third-party API
    (e.g., Shareus, Droplink), redirecting users through verification challenges
    before granting access.

3.1 Persistent Storage Queue Mechanics (storage_jobs.py)
--------------------------------------------------------------------------------
The durable storage queue guarantees zero file loss even during process crashes,
container restarts, or extended Telegram outages.

  - Authoritative Queue vs. Execution Buffer:
    * MongoDB `storage_jobs` is the authoritative, durable queue.
    * `asyncio.Queue` in `StorageService` is strictly a transient in-memory buffer.
    * If the process crashes, the in-memory buffer is lost, but all jobs remain
      intact in MongoDB.

  - Complete Storage Job Document Schema:
    ```json
    {
      "_id": ObjectId("66f2d8000000000000000001"),
      "job_id": "66f2d8000000000000000001:STORE_TO_FLOG",
      "storage_operation_key": "66f2d8000000000000000001:STORE_TO_FLOG",
      "db_id": "66f2d8000000000000000001",
      "file_id": "BAACAgIAAxkBAAI...",
      "user_id": 123456789,
      "status": "PENDING",
      "priority": 0,
      "attempts": 0,
      "max_attempts": 3,
      "lease_until": null,
      "worker_id": null,
      "assigned_client_id": null,
      "created_at": 1727188800.0,
      "updated_at": 1727188800.0,
      "next_retry_at": 1727188800.0,
      "error": null,
      "is_folder_file": false,
      "folder_id": null,
      "folder_session_id": null,
      "metadata": {
        "file_name": "sample.mkv",
        "file_size": 52428800
      }
    }
    ```

  - State Transition Matrix:
    * `PENDING` -> Job awaiting worker assignment.
    * `CLAIMED` -> Worker acquired atomic lease via `find_one_and_update`.
    * `RUNNING` -> Worker actively transferring media to FLOG channel.
    * `STORED`  -> Media verified in FLOG channel; terminal success state.
    * `FAILED`  -> Transfer failed; scheduled for exponential backoff retry.
    * `DEAD_LETTER` -> Exceeded `max_attempts` (3); requires admin intervention.
    * `CANCELLED`   -> User or admin cancelled parent session/job.

3.2 Atomic Lease Ownership, Heartbeats & Expired Lease Recovery
--------------------------------------------------------------------------------
  - Atomic Claiming (`claim_next_storage_job`):
    Workers claim jobs using an atomic MongoDB find-and-modify operation:
    ```python
    job = await col.find_one_and_update(
        {
            "status": "PENDING",
            "next_retry_at": {"$lte": now},
            "$or": [
                {"lease_until": None},
                {"lease_until": {"$lt": now}}
            ]
        },
        {
            "$set": {
                "status": "CLAIMED",
                "worker_id": worker_id,
                "lease_until": now + lease_duration_seconds,
                "updated_at": now
            },
            "$inc": {"attempts": 1}
        },
        sort=[("priority", pymongo.DESCENDING), ("created_at", pymongo.ASCENDING)],
        return_document=ReturnDocument.AFTER
    )
    ```
    This guarantees that two workers can never claim the same job simultaneously.

  - Lease Heartbeats & Renewal:
    While transferring large files, workers invoke `renew_job_lease(job_id, worker_id, 300)`.
    If a worker crashes, its heartbeat ceases.

  - Expired Lease Recovery (`recover_expired_leases`):
    A background supervisor periodically scans for stranded jobs:
    `status in ["CLAIMED", "RUNNING"] and lease_until < now`.
    Stranded jobs are reset to `status = "PENDING"` and `lease_until = None`,
    allowing surviving workers to re-claim and complete them.

3.3 Multi-Channel FLOG Architecture & Continuous Reconciliation (flog_sync.py)
--------------------------------------------------------------------------------
Storage redundancy is achieved via dual storage channels:
  - `FLOG_CHANNEL`: Primary storage channel for public files.
  - `ADMIN_FLOG_CHANNEL`: Isolated fallback channel for administrative users.
  - `resolve_active_flog_target(db, user_id)`: Routes files dynamically based on
    user administrative privileges (`db.is_admin_flog_user(user_id)`).

Continuous FLOG Reconciliation Daemon (`flog_sync.py`):
Runs every 300 seconds, detecting and repairing 8 discrepancy classes:
  1. `MISSING_FLOG_REFERENCE`: File in MongoDB references deleted/empty message
     in Telegram channel -> purged from MongoDB.
  2. `ORPHAN_FLOG_MESSAGE`: Message exists in Telegram but missing in Mongo.
  3. `MISMATCHED_FLOG_REFERENCE`: File doc references incorrect channel ID.
  4. `UNSETTLED_STORAGE_JOB`: Long-running non-terminal storage job.
  5. `STORED_FILE_PENDING_JOB`: Crash-after-FLOG recovery (file uploaded to Telegram
     before process crash; job status updated to STORED).
  6. `FAILED_JOB_WITH_FLOG`: Job marked failed/dead-letter, but FLOG message exists.
  7. `EXPIRED_LEASE`: Job lease expired; recovered to PENDING.
  8. `STALE_STORAGE_STATUS`: File document marked PENDING while storage job is STORED.

3.4 Multi-Tier File Caching (runtime_cache.py & stream_cache.py)
--------------------------------------------------------------------------------
The caching architecture operates across three levels:

  1. In-Memory Runtime Metadata Cache (`runtime_cache.py`):
     - `_FILE_INFO_CACHE`: Stores raw file documents (TTL = 30s).
     - `_FILE_REFERENCE_CACHE`: Stores public link resolution results (TTL = 15s).
     - `_FLOG_VALIDATION_CACHE`: Caches Telegram message existence checks (TTL = 5s).
     - All read operations return deep copies (`copy.deepcopy`) to prevent in-memory
       mutation leaks.

  2. Local Disk Media Chunk Cache (`stream_cache.py`):
     - Enabled via `Server.STREAM_LOCAL_CACHE_ENABLED = True`.
     - Chunks stored under `Server.STREAM_CACHE_DIR/{safe_key[:2]}/{safe_key}/{offset:020d}.chunk`.
     - In-flight request deduplication: Multiple concurrent requests for the same
       byte offset attach to a single `asyncio.Future`, preventing duplicate DC downloads.
     - LRU Cache Pruning: Periodically scans cache directory, purging oldest
       chunks when total size exceeds `Server.STREAM_CACHE_MAX_GB`.

  3. ByteStreamer Cache (`custom_dl.py`):
     - `cached_file_ids`: Caches Pyrogram `FileId` representations per file ID.
     - Automatically cleans entries older than 30 minutes.

4.2 HTTP Range Header Parser, Socket Tuning & Parallel Prefetching
--------------------------------------------------------------------------------
`_parse_range(range_header, file_size)` parses client byte requests:
  - Format 1 (Standard Range): `bytes=0-1048575` -> `(0, 1048575)`.
  - Format 2 (Open Suffix): `bytes=1048576-` -> `(1048576, file_size - 1)`.
  - Format 3 (Tail Bytes): `bytes=-524288` -> `(file_size - 524288, file_size - 1)`.
  - Content-Range Header Construction:
    `Content-Range: bytes {from_bytes}-{until_bytes}/{file_size}`
    accompanied by HTTP 206 Partial Content.

Content-Disposition Header Construction:
Complies with RFC 6266 and RFC 5987 for international filename support:
```
Content-Disposition: attachment; filename="{sanitized_ascii}"; filename*=UTF-8''{url_encoded_utf8}
```

Socket Tuning & High-Throughput Range Streaming:
  - `TCP_NODELAY` Socket Optimization: Disabled Nagle's algorithm on `request.transport` socket
    to eliminate the 40ms packet coalescing latency penalty, flushing media chunks to clients immediately.
  - In-Memory LRU Chunk Ring-Buffer (`stream_cache._mem_cache`): Keeps recently fetched and prefetched
    chunks in RAM (up to 64MB) for instant 0ms retrieval before falling back to local NVMe/SSD chunk cache.
  - Async Sliding-Window Prefetch Engine (`schedule_prefetch_window`): When chunk N is requested,
    background asyncio tasks immediately prefetch chunks N+1..N+4 across secondary bot clients (`multi_clients`)
    in round-robin fashion, bypassing per-client Telegram DC rate limits and saturating client bandwidth.

4.3 Fast Video Scrubbing & Tail moov-Atom Virtualization (mp4_metadata.py)
--------------------------------------------------------------------------------
Problem:
Many MP4 files uploaded to Telegram have their `moov` atom (index metadata) located
at EOF (tail) rather than the beginning (`ftyp` -> `moov` -> `mdat`). Standard web
browsers requesting progressive MP4 playback perform multiple HTTP 206 range requests
to the file tail (~512KB - 2MB) before video playback can start. Over high-latency
Telegram MTProto connections, this incurs 3-10s initial buffering lag and scrub stalls.

Solution & Engine Architecture:
  1. Top-Level ISO/IEC 14496-12 Box Parser (`find_boxes`, `find_moov_atom`):
     - Parses top-level atom boxes: `ftyp`, `moov`, `mdat`, `free`, `skip`.
     - Scans the initial 128KB header and final 2MB tail (`Server.MP4_MOOV_TAIL_SCAN_MB`)
       via `ByteStreamer`.
     - Detects atom boundaries and marks `is_tail=True` when `moov` succeeds `mdat`.

  2. Chunk Offset Patcher (`patch_moov_chunk_offsets`):
     - In-place binary rewriting of MP4 sample tables for atom repositioning.
     - Supports both 32-bit `stco` boxes and 64-bit `co64` boxes.
     - Automatically shifts table offset pointers by the byte length of the injected
       `moov` atom, preventing media track synchronization errors.

  3. Two-Tier Metadata Caching (`MP4MetadataManager`):
     - Disk Cache: Persists extracted/patched `moov` atom blobs and metadata dictionaries
       to disk under `Server.STREAM_CACHE_DIR/moov/{file_id}.json` and `.moov`.
     - In-Memory Cache: Keeps active metadata maps in RAM for sub-millisecond lookup.

  4. Instant HTTP 206 Range Interception:
     - In `stream_routes.py:media_streamer()`, incoming HTTP 206 byte-range requests
       intersecting header (`ftyp`) or tail (`moov`) byte offsets are served instantly
       from local cache via `mp4_metadata_manager.get_cached_range()`.
     - Completely bypasses Telegram MTProto round-trips for metadata reads, reducing
       time-to-first-frame from 3-10s down to <100ms.

  5. Virtual Faststart Sequential Streaming (`virtual_faststart_stream` & `virtual_faststart_range_stream`):
     - Sequential Generator (`virtual_faststart_stream`): Yields `ftyp -> patched moov -> mdat` on-the-fly.
       Allows downstream FFmpeg stdin pipes (`pipe:0`) to ingest MTProto video streams
       sequentially without requiring random seeks or intermediate full-file downloads.
     - HTTP 206 Virtual Range Streamer (`virtual_faststart_range_stream`):
       Seamlessly maps arbitrary client byte ranges `[from_bytes, until_bytes]`. For initial header/index
       requests (`until_bytes < prefix_len`), bytes are served directly from RAM (`header_data + patched_moov`).
       For data requests intersecting or inside `mdat` (`from_bytes >= prefix_len`), maps virtual offsets
       to MTProto file offsets (`from_bytes - moov_size`) with strict 1024-byte aligned chunk fetching.
     - Preserves true original file size in `Content-Range: bytes X-Y/file_size` and `Content-Length`.
     - In `stream_routes.py:media_streamer()`, activates Virtual Faststart on progressive MP4 stream
       requests when `moov` is located at EOF, completely eliminating multi-second initial seeking/buffering delays.

4.4 Dynamic HLS Segmenter & Adaptive Bitrate (ABR) Pipeline (hls_service.py)
--------------------------------------------------------------------------------
To provide smooth playback across unstable cellular networks and eliminate format
incompatibilities (e.g. MKV, AVI, non-web MP4s on mobile Safari/Chrome):

  1. Multi-Variant Transcode Ladder:
     - `1080p`: Native source resolution (or 1920x1080 cap, 5000k bandwidth).
     - `720p`: 1280x720 downscale (2500k bandwidth, `-crf 23 -preset veryfast`).
     - `480p`: 854x480 mobile downscale (1000k bandwidth, `-crf 24 -preset veryfast`).

  2. Zero-Copy Fast-Path Remuxing:
     - `HLSService.probe_codec()` inspects incoming media via `ffprobe`.
     - If video codec is H.264 (`avc1`) and audio is AAC, native resolution executes
       stream copy (`-c:v copy -c:a copy -f hls`) bypassing heavy CPU transcode.
     - Generates compliant MPEG-TS segments with near-zero CPU overhead.

  3. Non-Blocking Asyncio FFmpeg Pipeline:
     - Spawns subprocess pipelines (`asyncio.create_subprocess_exec`) connected to
       `mp4_metadata_manager.virtual_faststart_stream()` via stdin feeder task.
     - Feeder feeds video chunks asynchronously, closing stdin cleanly upon completion.

  4. Concurrency Guardrails & Lifecycle Protection:
     - Transcoding Concurrency: Bounded by `asyncio.Semaphore(Server.HLS_MAX_TRANSCODES=3)`
       to prevent host CPU saturation.
     - Active Process Tracking: Each session is tracked in `HLSJob` with its process,
       feeder task, creation timestamp, and completion event.
     - Client Disconnect Handling: When a client drops or seeks, the job catches
       `asyncio.CancelledError` or client disconnect, terminating the FFmpeg sub-process
       and cleaning up feeder tasks immediately.
     - Background Reaper: An idle reaper task periodically evaluates active jobs,
       terminating any session inactive for > `Server.HLS_IDLE_TIMEOUT` (600s, preventing
       premature cancellation during multi-hour movie playback).
     - VOD Finalization: Upon completing transcoding, `#EXT-X-ENDLIST` is appended to finalize the playlist.

  5. VOD Playlist Virtualization & Instant Full-Length Seeking:
     - Upfront Virtual VOD Generation (`HLSService.generate_vod_playlist`):
       Computes total segments from file duration (`N = math.ceil(duration / seg_duration)`), generating
       full VOD `index.m3u8` upfront with `#EXT-X-PLAYLIST-TYPE:VOD` and `#EXT-X-ENDLIST`.
     - 0ms Initialization: The web player receives the manifest in 0ms without waiting for real-time
       transcode buffers, immediately unlocking the true full-length timeline (e.g. 02:52:14) rather
       than a live expanding timeline capped at 01:19.
     - On-Demand Segment Generation (`HLSService.ensure_segment`):
       When `/hls/{token}/{quality}/seg_{segment_id}.ts` is requested, the server extracts and encodes
       that specific 6s segment on-demand via loopback HTTP 206 range seeking (`/_internal/stream/{file_id}`).
     - Pre-Generation Pipeline: Each segment request triggers proactive background encoding for segment N+1,
       maintaining uninterrupted buffer ahead of playback without keeping long-running 3-hour FFmpeg processes.

  6. Segment Caching & Ring-Buffer Management:
     - Generated HLS segments and playlists are stored on disk under:
       `Server.STREAM_CACHE_DIR/hls/{file_id}/{quality}/seg_{segment_id}.ts`
     - Disk LRU Ring-Buffer: Evaluates cache size and purges older segment directories
       when disk thresholds are approached.
     - Security: All HLS routes validate ephemeral stream tokens and verify the
       `fs_page_session` cookie to prevent hotlinking and token hijacking.

4.5 Automated WebP Storyboards & Scrubbing Thumbnails (thumbnail_service.py)
--------------------------------------------------------------------------------
Provides interactive timeline scrubbing preview thumbnails in the web player:

  1. Consolidated Mosaic Sprite Sheet (`sprites.webp`):
     - Samples video frames at regular intervals (5-10s depending on duration).
     - Generates a single consolidated 10x10 tile mosaic sheet (160x90px per thumbnail)
       using FFmpeg filter: `fps=1/{interval},scale=160:90,tile=10x{rows}`.
     - Encoded in WebP format for optimal compression and rapid client loading.
     - Single-image mosaic replaces hundreds of individual HTTP image requests.

  2. WebVTT Storyboard Index (`thumbnails.vtt`):
     - Generates standard WebVTT timeline file mapping time intervals to sprite coordinates:
       ```
       WEBVTT
       00:00:00.000 --> 00:00:10.000
       /thumbnails/{token}/sprites.webp#xywh=0,0,160,90
       00:00:10.000 --> 00:00:20.000
       /thumbnails/{token}/sprites.webp#xywh=160,0,160,90
       ```

  3. Automated Background Generation Hook:
     - Asynchronous trigger in `file_service.py` (`_trigger_background_indexing`) kicks
       off thumbnail generation upon file ingestion into storage.
     - Lazy fallback trigger in `stream_routes.py` kicks off generation on initial
       user playback if not already cached.

4.6 Dynamic Template Rendering & Web Player Architecture (play.html)
--------------------------------------------------------------------------------
Templates in `FileStream/template/` are rendered dynamically via Jinja2:
  - `play.html`: Advanced media playback interface combining Plyr.js and HLS.js:
    * Self-Contained Offline Bundle: Local `FileStream/static/hls.min.js` and `plyr.js`.
    * Dual-Mode Engine Detection & Stream Mode Switcher:
      - Native Progressive Default: Intelligently detects browser playback capabilities (`is_native_playable`).
        For MP4/WebM files, defaults player source to native progressive HTTP 206 streaming (`/stream/{token}`),
        eliminating server CPU load and enabling instant scrubbing across multi-gigabyte files.
      - Adaptive HLS Engine: Reserves HLS as primary for non-native containers (MKV, AVI) and as an on-demand
        ABR fallback option via MSE (Chrome/Firefox/Android) and native HLS (Safari/iOS).
      - Interactive Stream Mode Switcher: Top toolbar buttons ("⚡ Direct Stream" vs "🎛 Adaptive HLS") allow
        instant mode switching while preserving exact playback position (`currentTime`).
    * True Full-Length Timeline Duration Lock:
      - Prevents in-progress HLS event playlists from collapsing or incrementally truncating the scrub bar.
      - Locks the duration to the authoritative container metadata via `Object.defineProperty(player, 'duration', ...)`

    * Dynamic Quality Selection:

      - Updates active level dynamically on user selection (`hls.currentLevel = quality`).
    * Timeline Scrubbing Thumbnails:

      - Renders live WebP thumbnail previews at hover position along the playback timeline.

  - `dl.html`: Direct download landing card displaying filename, formatted file

  - `folder.html`: Grid layout displaying folder title, item count, total size,

4.7 Web Security Middleware, Path Sanitization & Client Disconnect Recovery
--------------------------------------------------------------------------------
  - Path Traversal Sanitization (`sanitize_download_path`):
    Inspects URL paths, rejecting `../`, `..\`, `%2e%2e`, and paths > 512 chars.
  - Scanner Probe Blocking (`is_suspicious_path`):
    Blocks requests matching known scanner targets: `/.env`, `/.git`, `/wp-admin`,
    `/.aws/credentials`, `/etc/passwd`, `/actuator`, etc.
  - Client Disconnect Recovery:
    When a web client aborts a stream (e.g., closing browser tab or seeking):
      1. Catches `asyncio.CancelledError` and `ConnectionResetError`.
      2. Cancels pending background chunk prefetch tasks and FFmpeg feeder pipes.
      3. Decrements client workload counter `work_loads[index]`.
      4. Closes media sessions without leaking open sockets or zombie child processes.

--------------------------------------------------------------------------------
File To Link V2 runs on a unified, high-efficiency asynchronous architecture:

    operations via `AuditTaskManager`.

The database initializes compound indexes during startup via `db.ensure_indexes()`
to ensure O(1) or O(log N) lookup performance:

    * `(flog_msg_id: 1)` & `(flog_channel_id: 1, flog_msg_id: 1)` -> FLOG sync.
    * `(user_id: 1, is_folder_file: 1, _id: -1)` -> Separates folder items from
